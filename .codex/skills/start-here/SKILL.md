# start-here

Turn an unfamiliar repo into a one-screen brief a human (and the agent) can act on.

## When to run

- User: `/start-here`, `where do I start`, `how do I run this`, `what is this repo`, `which file do I change for <task>`
- First message in a repo that has no `START_HERE.md` (offer once; do not nag)
- After a big merge that changes entrypoints (offer regenerate)

## Hard rules

1. **Prose + tables only.** Never emit Mermaid, node graphs, JSON dumps, or architecture diagrams.
2. **Fits on one screen** (~80–120 lines). If longer, cut.
3. **Evidence from files only.** Read real paths and real npm/cargo/go/py scripts. If unsure, say `unknown`.
4. **Never invent run commands.** Prefer `package.json` scripts, `Makefile`, `justfile`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `docker-compose.yml`, CI workflow.
5. **Task → file map must name real paths** (max 8 tasks). Prefer `src/`, route/handler files, UI pages, and the test that covers them.
6. **Write `START_HERE.md` at repo root** unless user asked for stdout only. Do not overwrite without asking if file exists and differs materially.
7. **Idempotent:** regenerating updates the same file.

## Procedure

### 1. Identify (≤15 cheap reads)

Scan in this order; stop when you have enough:

| Signal | What you get |
|--------|----------------|
| `README*` | purpose, install |
| `package.json` / `pyproject.toml` / `Cargo.toml` / `go.mod` / `pom.xml` / `build.gradle*` | name, scripts, deps |
| `Makefile` / `justfile` / `Taskfile*` | canonical commands |
| Top-level dirs (`src/`, `app/`, `packages/`, `services/`) | layout |
| `docker-compose*.yml` / `Dockerfile` | services, ports |
| `.github/workflows/*` | CI truth |
| One entry file (`main.*`, `index.*`, `app.*`, `cmd/`) | boot path |
| Existing `CLAUDE.md` / `AGENTS.md` | prior context |

Ignore: `node_modules`, `vendor`, `dist`, `build`, lockfiles, assets, generated code.

### 2. Infer task map

Map each applicable row to a **real path** (omit rows that don't apply):

| Task | Look for |
|------|----------|
| Add/change API or route | router, `controllers/`, `routes/`, `app/api/`, handlers |
| Change UI | `pages/`, `views/`, `components/`, templates |
| Change data/schema | `models/`, `schema*`, `migrations/`, `prisma/`, SQL |
| Fix a bug in <domain> | file owning that path + nearest test |
| Add a test | files matching `*.test.*`, `*.spec.*`, `*_test.*`, `test_*.py`, or dirs `tests/`, `__tests__/` — never match names like `Testimonials` |
| Config / env | `.env.example`, `config/`, settings modules |
| Deploy | Dockerfile, CI, `deploy/`, fly/railway/render configs |
| Local dev loop | run script + hot-reload + test command |

If user passed a task string, put **that task first** and expand 1–2 lines of concrete next steps (file to open, symbol to find).

### 3. Write `START_HERE.md`

Use this skeleton exactly (fill, don't pad):

```markdown
# Start here

> Generated by [start-here](https://github.com/Lubnaaziz-28/start-here) · <YYYY-MM-DD>

## What this is
<1–2 sentences. Noun phrase purpose. No marketing.>

## Run it
| Step | Command |
|------|---------|
| Install | `<from real manifest>` |
| Dev | `<or unknown>` |
| Test | `<or unknown>` |
| Build | `<or unknown>` |

Stack: `<language>` · `<framework if any>` · `<db/host if obvious>`

## Where to change what
| I want to… | Open |
|------------|------|
| … | `path/to/file` (and test `path`) |

## First PR (suggested)
<1–3 sentences: smallest safe change a newcomer can land. Point at a real TODO, failing test, or docs gap — or say "run the test suite green is enough.">

## Gotchas
- <env vars, monorepo workspace rules, ports, "don't touch generated/" — only if found>

## Layout (optional, ≤6 bullets)
- `path/` — one line each, only top-level that matter
```

If anything is unknown, write `unknown` — do not guess.

### 4. Deliver

1. Write `START_HERE.md` at repo root.
2. Reply with the file path + the **Run it** table inline (so the user sees value without opening the file).
3. If the user asked a specific task ("where do I change auth?"), answer that first in chat, then persist the file.

## Anti-patterns

- Don't dump a full dependency tree or directory listing.
- Don't recommend tools the repo doesn't use.
- Don't write "This project is a modern scalable solution…" — cut adjectives.
- Don't run the app unless asked; `START_HERE.md` is static recon.
- Don't create other files (`ARCHITECTURE.md`, graphs, JSON).

## Regeneration

`/start-here --force` → overwrite existing `START_HERE.md` after a 3-line diff summary of what changed.
